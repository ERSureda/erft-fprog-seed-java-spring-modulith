## 1. Problem Statement
La validación duplicada (repetir en el `*Command` lo que Bean Validation `@Valid` ya revisó en el controlador web) genera sobrecoste y código redundante. Por el contrario, omitir validación en comandos permite que payloads corruptos desde colas o schedulers alcancen la base de datos.

## 2. Decision Matrix
| Directiva | Regla | Especificación Técnica |
| :--- | :---: | :--- |
| **`MUST`** | `APP-03` | Clasificar explícitamente cada comando en `API.md` como `WEB_EXCLUSIVE` o `MULTICHANNEL`. |
| **`MUST`** | `APP-03` | Comandos `WEB_EXCLUSIVE`: declarados como `record` inmutables planos sin validación interna; validación delegada a Bean Validation (`@Valid`, `@NotNull`) en `*HttpRequest`. |
| **`MUST`** | `INP-01` | Mapeo de petición web a comando mediante método de instancia directo `request.toCommand(...)` en el propio DTO. Cero MapStruct en web. |
| **`MUST`** | `APP-03` | Comandos `MULTICHANNEL` (Workers, Schedulers, Sync Ports): validación *fail-fast* obligatoria en constructor compacto mediante `Objects.requireNonNull(field, "TOKEN_STRUCTURED")`. |
| **`MUST`** | `SHR-04` | Gramática de tokens para fallos defensivos: `[ENTIDAD]_[CAMPO]_[REGLA]` (ej. `ORDER_CUSTOMER_ID_CANNOT_BE_NULL`). |
| **`NEVER`** | `INP-01` | Usar mappers dinámicos o MapStruct en adaptadores primarios web. |

## 3. Canonical Flow
```text
CANAL 1: Comandos Exclusivamente Web (WEB_EXCLUSIVE)
  *HttpRequest (@NotNull, @Size...) ──► @Valid en Controller ──► request.toCommand() ──► *Command plano

CANAL 2: Comandos Multicanal (MULTICHANNEL: Workers, Schedulers, Sync Ports)
  Worker / Scheduler / Inter-Module ──► *Command(constructor compacto: Objects.requireNonNull con TOKEN)
```

## 4. Trade-Offs & Mitigations
* **Sobrecarga de Clasificación:** El equipo debe clasificar cada comando según su canal.
  * *Mitigación:* La plantilla `API.md` (Fase 1 Rails) exige definir la columna `Canal` para cada comando antes de codificar.
